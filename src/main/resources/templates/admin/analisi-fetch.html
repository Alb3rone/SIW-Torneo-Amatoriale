Analisi sperimentale: strategie di fetch

Caso d'uso: caricamento di tutte le squadre con i relativi giocatori. Confronto tra strategia LAZY (default) e strategia JOIN FETCH. Squadre caricate: 0.

LAZY (default)

Carica le relazioni solo quando vengono accedute. Genera il problema N+1 query: una query per caricare le squadre, poi una query aggiuntiva ogni volta che accediamo alla collezione dei giocatori di una squadra.

JOIN FETCH

Carica squadre e giocatori con una singola query. Elimina il problema dell'N+1: quando dopo si accede a squadra.getGiocatori() i dati sono gia' in memoria, nessuna query aggiuntiva viene emessa.

Conclusioni

La strategia JOIN FETCH risulta piu' efficiente per il caso d'uso "elenco squadre con giocatori" perche' esegue una sola round-trip verso il database, mentre la strategia LAZY paga il costo di N query aggiuntive (una per ogni squadra).

Il vantaggio del LAZY, che pero' qui e' irrilevante, e' quando la relazione non viene mai acceduta: in quel caso non paghiamo il costo del JOIN. Regola pratica: usa JOIN FETCH quando SEI SICURO che il codice accedera' alla relazione (es. lista da mostrare in tabella); lascia LAZY quando l'accesso e' condizionato o raro.

Nota: i valori temporali sono influenzati dalla cache di primo livello di Hibernate. Alla seconda esecuzione della pagina, il LAZY potrebbe apparire piu' veloce perche' le entita' sono gia' in cache. Per una misura piu' realistica bisognerebbe svuotare il persistence context tra le due esecuzioni.
